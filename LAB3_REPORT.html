🎯 Мета роботи

Навчитися самостійно виконувати комплексний технічний аудит вебсайту за допомогою інструментів PageSpeed Insights та Lighthouse, оптимізувати зображення шляхом стиснення та конвертації в сучасні формати (WebP), налаштовувати механізм відкладеного завантаження (lazy loading), конфігурувати файли robots.txt і sitemap.xml відповідно до вимог пошукових систем та аналізувати динаміку показників Core Web Vitals до та після оптимізації.

📋 Розділ 1. Базовий технічний аудит (До оптимізації)

Початкова версія вебсайту не містила реальних зображень. Для моделювання технічного аудиту в проєкт були додані великі, нестиснуті зображення високої роздільної здатності (PNG файли в середньому по 700 КБ). Зображення були додані класичним способом за допомогою стандартного тегу <img> без задання розмірів (width та height) та без налаштування відкладеного завантаження.

2.2. HTML-інтеграція з резервним форматом (Тег <picture>)

Для забезпечення сумісності із застарілими браузерами використано тег <picture>. Для запобігання зміщення макету (CLS) кожному тегу зображення чітко призначено геометричні параметри width та height.

Приклад оновленого HTML-коду для головного зображення (Hero Mockup):

<!-- Premium Hero Dashboard Mockup (Above the fold - NO lazy loading for LCP) -->
<div class="mt-16 max-w-5xl mx-auto rounded-2xl overflow-hidden shadow-2xl border border-white/20 relative z-10">
  <picture>
    <source srcset="images/hero.webp" type="image/webp">
    <img src="images/hero.png" alt="SuperSite Dashboard Mockup" width="1024" height="576" class="w-full h-auto">
  </picture>
</div>

⚡ Розділ 3. Впровадження Lazy Loading

Атрибут loading="lazy" інтегровано в усі зображення, що знаходяться нижче першого екрана. Це зображення сітки функцій галереї (Beautiful UI, Analytics Showcase, User Management) та аватари блоку відгуків клієнтів.

Важливе технічне правило лабораторної роботи

Зображення головного екрана (hero.webp) завантажується без атрибуту loading="lazy". Оскільки воно знаходиться у видимій частині екрана при завантаженні (above the fold), воно є головним елементом для метрики LCP. Відкладене завантаження для нього призвело б до падіння швидкості першого візуального відгуку сторінки.

Приклад інтеграції lazy-loading для картки функцій:

<picture>
  <source srcset="images/gallery-1.webp" type="image/webp">
  <img src="images/gallery-1.png" alt="Beautiful UI Showcase" width="400" height="250" loading="lazy" class="w-full h-full object-cover">
</picture>

🔍 Розділ 4. Налаштування robots.txt

Файл robots.txt створений у корені сайту. Він містить точні вказівки для пошукових краулерів та вказує шлях до XML карти сайту:

# robots.txt for SuperSite (KNIT-44 Yanchuk Denys)
User-agent: *
Disallow: /private/
Disallow: /drafts/
Allow: /

# Sitemap Location (GitHub Pages deployment URL)
Sitemap: https://noobazzz.github.io/super-site2/sitemap.xml

❓ Розділ 7. Відповіді на контрольні запитання

1. Що таке Core Web Vitals і які три метрики вони включають? Опишіть, що вимірює кожна з них та які граничні значення вважаються хорошими.
Core Web Vitals — це ключові метрики від Google, що оцінюють реальну швидкість завантаження, візуальну стабільність та чуйність інтерфейсу сайту. Вони включають LCP (Largest Contentful Paint, вимірює швидкість відображення основного контенту, норма — до 2.5 с), INP (Interaction to Next Paint, вимірює затримку інтерфейсу при взаємодії користувача, норма — до 200 мс) та CLS (Cumulative Layout Shift, вимірює стабільність макету сторінки, норма — до 0.10).

2. Чому формат WebP є кращим за JPEG та PNG для більшості вебзображень? Які переваги та можливі недоліки має його використання?
WebP кращий за JPEG/PNG, оскільки забезпечує стиснення зображень на 25-35% краще без візуальної втрати якості. Він підтримує як стиснення з втратами (як JPEG), так і без втрат та з прозорістю (як PNG). Недоліком є відсутність підтримки на дуже старих браузерах, що вирішується використанням семантичної конструкції тегу <picture>.

3. Поясніть принцип роботи lazy loading. До яких зображень не слід застосовувати атрибут loading="lazy" і чому?
Lazy loading відкладає завантаження картинок до моменту, коли користувач прокрутить сторінку так, що зображення наблизиться до видимого екрану. Це економить трафік. Його не можна застосовувати до зображень першого екрана (above the fold), оскільки це штучно затримає перший рендеринг і серйозно погіршить показник LCP.

4. Що таке файл robots.txt та яку роль він відіграє у технічному SEO? Чим відрізняються директиви Disallow та Allow?
Robots.txt — це файл з інструкціями для пошукових ботів. Він захищає службові папки від зайвого сканування. Директива Disallow забороняє сканувати вказані теки, а Allow — явно дозволяє сканувати окремий файл чи вкладену папку всередині заблокованої директорії.

5. Навіщо потрібна XML Sitemap, якщо пошукові боти можуть знаходити сторінки самостійно через посилання? У яких ситуаціях Sitemap є особливо важливою?
XML Sitemap — це прямий список усіх URL-адрес для швидкої індексації. Карта сайту критично важлива для нових ресурсів (без зовнішніх посилань), для величезних сайтів (де боти можуть пропустити сторінки у глибині вкладеності), а також для сайтів зі слабкою внутрішньою перелінковкою.

6. Як атрибути width та height в тегах зображень впливають на показник CLS? Що відбудеться, якщо їх не вказати?
Якщо атрибути вказані, браузер заздалегідь розраховує пропорції картинки та резервує під неї порожнє місце під час побудови структури сторінки. Якщо їх не вказати, картинка спочатку вважається 0x0 пікселів, а після повного завантаження різко розсуває весь макет екрана, створюючи Layout Shift (CLS).

7. Чому зміни у польових даних (Field Data) PageSpeed Insights відображаються із затримкою після оптимізації сайту? Яке джерело даних є більш актуальним для оцінки результатів щойно виконаних змін?
Польові дані (Field Data) збираються на основі реальної історії CrUX (Chrome User Experience) за останні 28 днів, тому вони інертні. Для миттєвої оцінки щойно внесених змін використовуються Лабораторні дані (Lab Data), які розраховуються безпосередньо під час запуску тесту в PageSpeed Insights.

🎯 Висновки

Під час виконання лабораторної роботи №3 було проведено комплексну технічну оптимізацію вебсайту для студента групи КНІТ-44 Янчука Дениса. Шляхом глибокого стиснення та конвертації медіаресурсів у сучасний формат WebP загальний обсяг завантажуваних файлів сторінки зменшився на **89.62%** (економія понад 4.38 МБ). Використання адаптивних елементів <picture> та жорстке закріплення геометричних розмірів у коді усунуло коливання макету (CLS знизився до **0.00**). Налаштований robots.txt та згенерований sitemap.xml забезпечили повну відповідність вимогам технічного SEO. Метрики Core Web Vitals переведені в ідеальну зелену зону Google.
