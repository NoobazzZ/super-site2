## 📁 Розділ 1. Базовий технічний аудит (До оптимізації)
Початкова інтеграція зображень була виконана без жодної технічної оптимізації: використовувалися важкі нестиснуті файли PNG/JPEG, звичайні теги `<img>` без атрибутів `width`/`height` та без відкладеного завантаження (`loading="lazy"`).

### 1.1. Показники Core Web Vitals до оптимізації
За результатами тестування через PageSpeed Insights (симуляція низькошвидкісного мобільного з'єднання 3G/4G та десктопу) було зафіксовано такі початкові лабораторні дані:

| Метрика | Mobile (До) | Desktop (До) | Норма Google | Оцінка статусу |
|---------|-------------|--------------|--------------|----------------|
| **Performance Score** | **68 / 100** | **82 / 100** | 90+ | Потребує покращення |
| **LCP (Largest Contentful Paint)** | **4.5 с** | **2.3 с** | до 2.5 с | ❌ Погано (для Mobile) |
| **INP (Interaction to Next Paint)**| **180 мс** | **80 мс** | до 200 мс | ✅ Добре |
| **CLS (Cumulative Layout Shift)**  | **0.28** | **0.25** | до 0.10 | ❌ Погано ( Layout Shift) |
| **FCP (First Contentful Paint)**   | **2.1 с** | **1.0 с** | до 1.8 с | ⚠️ Посередньо |
| **TTFB (Time to First Byte)**     | **250 мс** | **90 мс** | до 800 мс | ✅ Добре |

### 1.2. Виявлені рекомендації Google PageSpeed Insights:
1. **Serve images in next-gen formats (Подавайте зображення в сучасних форматах):** Попередження про те, що використання форматів PNG та JPEG збільшує обсяг завантажуваних даних. Рекомендовано конвертувати зображення в WebP або AVIF.
2. **Properly size images (Налаштуйте правильний розмір зображень):** Деякі зображення завантажуються у роздільній здатності, що значно перевищує розміри їх відображення на екрані.
3. **Defer offscreen images (Відкладіть завантаження прихованих зображень):** Зображення галереї та аватари відгуків знаходяться нижче першого екрана прокручування, проте завантажуються одразу при відкритті сторінки, блокуючи основний потік.
4. **Avoid cumulative layout shifts (Уникайте значних зміщень макету):** Теги зображень не мають атрибутів `width` та `height`, через що браузер не може зарезервувати під них місце до завантаження файлу. Це призводить до різкого "стрибка" контенту вниз при появі зображення (CLS = 0.28).

### 2.2. HTML-інтеграція з резервним форматом (Тег `<picture>`)
Для забезпечення повної сумісності (включаючи застарілі браузери) використано семантичний тег `<picture>`, який надає браузеру вибір: завантажити сучасний формат WebP, а якщо він не підтримується — завантажити класичний JPEG/PNG як резервний (fallback).

Для усунення CLS (зміщення макету) для кожного зображення чітко задано геометричні атрибути `width` та `height` відповідно до пропорцій зображення.

#### Приклад інтеграції Hero-зображення (без lazy loading, оскільки це LCP-елемент):
```html
<picture>
  <source srcset="images/hero.webp" type="image/webp">
  <img src="images/hero.png" alt="SuperSite Dashboard Mockup" width="1024" height="576" class="w-full h-auto">
</picture>
```

#### Приклад інтеграції галерейного зображення (нижче лінії прокручування, з lazy loading):
```html
<picture>
  <source srcset="images/gallery-1.webp" type="image/webp">
  <img src="images/gallery-1.png" alt="Beautiful UI Showcase" width="400" height="250" loading="lazy" class="w-full h-full object-cover">
</picture>
```

## ⚡ Розділ 3. Налаштування Lazy Loading
Lazy loading (відкладене завантаження) — це критично важлива техніка технічного SEO, що запобігає завантаженню медіаресурсів, які користувач ще не бачить у своєму вікні перегляду (viewport).

### 3.1. Стратегія впровадження:
- **Hero Image (Головний екран):** Атрибут `loading="lazy"` **НЕ застосовувався**. Це зображення є основним елементом першого екрана. Його відкладене завантаження призвело б до критичного збільшення показника LCP (Largest Contentful Paint), оскільки браузер чекав би на побудову дерева DOM та макетування перед початком завантаження медіафайлу.
- **Зображення галереї та Аватари (Нижче лінії прокручування):** Атрибут `loading="lazy"` **успішно інтегровано** у всі відповідні теги `<img>`.

### 3.2. Перевірка роботи в DevTools:
Перевірка здійснювалася у вкладці **Network** (Фільтр: `Img`) браузера Google Chrome:
1. При початковому завантаженні сторінки завантажується лише `hero.webp`.
2. Завантаження `gallery-1.webp`, `gallery-2.webp` та `gallery-3.webp` ініціюється автоматично лише тоді, коли користувач починає прокручувати сторінку вниз і секція "Amazing Features" наближається до видимої області.
3. Аватари відгуків (`avatar-1.webp`, `avatar-2.webp`, `avatar-3.webp`) завантажуються в останню чергу, безпосередньо перед наближенням до підвалу (footer) сайту.

## 🔍 Розділ 4. Технічне SEO: Файл robots.txt
Файл `robots.txt` створено в кореневій директорії сайту. Він містить точні вказівки для пошукових роботів, обмежуючи доступ до службових або закритих папок та вказуючи абсолютне посилання на XML Sitemap.

### 4.1. Вміст файлу `robots.txt`:
```
# robots.txt for SuperSite (KNIT-44 Yanchuk Denys)
User-agent: *
Disallow: /private/
Disallow: /drafts/
Allow: /

# Sitemap Location (GitHub Pages deployment URL)
Sitemap: https://noobazzz.github.io/super-site2/sitemap.xml
```

### 4.2. Пояснення директив:
- `User-agent: *` — правила застосовуються до всіх пошукових роботів (Googlebot, Bingbot, YandexBot тощо).
- `Disallow: /private/` — заборона індексувати вміст папки приватних даних.
- `Disallow: /drafts/` — заборона сканувати чернетки публікацій, які ще не готові для користувачів.
- `Allow: /` — дозволяє індексувати всі інші сторінки сайту.
- `Sitemap: https://...` — вказує пошуковим системам точне місце знаходження карти сайту для прискорення індексації.

## 🗺️ Розділ 5. Технічне SEO: XML Sitemap
XML-карта сайту `sitemap.xml` була згенерована для забезпечення швидкого виявлення та індексування всіх сторінок пошуковими роботами Googlebot.

### 5.1. Повний вміст файлу `sitemap.xml`:
```xml
<?xml version="1.0" encoding="UTF-8"?>
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  <url>
    <loc>https://noobazzz.github.io/super-site2/</loc>
    <lastmod>2026-05-26</lastmod>
    <changefreq>weekly</changefreq>
    <priority>1.0</priority>
  </url>
  <url>
    <loc>https://noobazzz.github.io/super-site2/index.html</loc>
    <lastmod>2026-05-26</lastmod>
    <changefreq>weekly</changefreq>
    <priority>0.9</priority>
  </url>
  <url>
    <loc>https://noobazzz.github.io/super-site2/dashboard.html</loc>
    <lastmod>2026-05-26</lastmod>
    <changefreq>daily</changefreq>
    <priority>0.8</priority>
  </url>
  <url>
    <loc>https://noobazzz.github.io/super-site2/posts.html</loc>
    <lastmod>2026-05-26</lastmod>
    <changefreq>daily</changefreq>
    <priority>0.8</priority>
  </url>
  <url>
    <loc>https://noobazzz.github.io/super-site2/users.html</loc>
    <lastmod>2026-05-26</lastmod>
    <changefreq>weekly</changefreq>
    <priority>0.7</priority>
  </url>
  <url>
    <loc>https://noobazzz.github.io/super-site2/profile.html</loc>
    <lastmod>2026-05-26</lastmod>
    <changefreq>weekly</changefreq>
    <priority>0.7</priority>
  </url>
  <url>
    <loc>https://noobazzz.github.io/super-site2/login.html</loc>
    <lastmod>2026-05-26</lastmod>
    <changefreq>monthly</changefreq>
    <priority>0.5</priority>
  </url>
  <url>
    <loc>https://noobazzz.github.io/super-site2/register.html</loc>
    <lastmod>2026-05-26</lastmod>
    <changefreq>monthly</changefreq>
    <priority>0.5</priority>
  </url>
</urlset>
```

### 5.2. Обґрунтування структури та параметрів:
- `<loc>` — містить повний абсолютний URL кожної сторінки сайту із протоколом HTTPS.
- `<lastmod>` — дата останньої модифікації файлу (2026-05-26).
- `<changefreq>` — очікувана частота оновлення. Головна сторінка та панелі керування/пости (`dashboard.html`, `posts.html`) оновлюються частіше (`daily`, `weekly`), сторінки входу/реєстрації — вкрай рідко (`monthly`).
- `<priority>` — пріоритет індексації (від 0.0 до 1.0). Головна сторінка має найвищий пріоритет (1.0), панель керування — 0.8, другорядні сторінки авторизації — 0.5.

## ❓ Розділ 7. Відповіді на контрольні запитання

### 1. Що таке Core Web Vitals і які три метрики вони включають? Опишіть, що вимірює кожна з них та які граничні значення вважаються хорошими.
**Core Web Vitals** — це набір критично важливих уніфікованих метрик швидкості та зручності інтерфейсу від Google, що безпосередньо впливають на позиції сайту в пошуковій видачі (SEO ranking factors).
Вони включають три ключові показники:
- **LCP (Largest Contentful Paint)** — вимірює швидкість завантаження основного вмісту сторінки. Вказує час, за який відображається найбільший видимий блок контенту (зазвичай це hero-зображення або великий заголовок).
  * *Норма:* **до 2.5 секунди** — добре. Від 2.5 до 4.0 с — потребує покращення. Понад 4.0 с — погано.
- **INP (Interaction to Next Paint)** — вимірює чуйність інтерфейсу на дії користувача (кліки, тапи, введення тексту) до моменту оновлення наступного кадру на екрані. Замінив метрику FID у березні 2024 року.
  * *Норма:* **до 200 мілісекунд** — добре. 200–500 мс — потребує покращення. Понад 500 мс — погано.
- **CLS (Cumulative Layout Shift)** — вимірює візуальну стабільність сторінки. Розраховує сумарний коефіцієнт незапланованих зміщень елементів макету під час завантаження.
  * *Норма:* **до 0.10** — добре. 0.10–0.25 — потребує покращення. Понад 0.25 — погано.

### 2. Чому формат WebP є кращим за JPEG та PNG для більшості вебзображень? Які переваги та можливі недоліки має його використання?
**WebP** — це сучасний формат стиснення зображень, розроблений Google спеціально для використання в інтернеті.
- **Переваги:**
  * **Вища ефективність стиснення:** Забезпечує на 25–35% менший розмір файлу порівняно з JPEG при аналогічній візуальній якості.
  * **Універсальність:** Підтримує як стиснення з втратами (lossy) для фотографій, так і стиснення без втрат (lossless) для графіки та прозорість (альфа-канал, як у PNG), а також анімацію (як у GIF).
  * **Швидкість рендерингу:** Швидше декодується браузерами, що зменшує навантаження на процесор.
- **Недоліки:**
  * Не підтримується дуже старими браузерами (наприклад, Internet Explorer або Safari версій до iOS 14 / macOS Big Sur). *Рішення:* Використання тегу `<picture>` з резервним (fallback) файлом JPEG/PNG.
  * При надмірному стисненні з втратами може з'являтися легке розмиття дрібних деталей (ефект блендингу кольорів).

### 3. Поясніть принцип роботи lazy loading. До яких зображень не слід застосовувати атрибут `loading="lazy"` і чому?
**Lazy loading (відкладене завантаження)** — це механізм, при якому браузер відкладає завантаження ресурсів (зображень, фреймів) до моменту, поки користувач не почне прокручувати сторінку, і цей ресурс не наблизиться до видимої області екрана (viewport). Це економить трафік користувача та прискорює початковий рендеринг сторінки.
- **До яких зображень не застосовувати:**
  * До зображень, що знаходяться у **першому екрані (above the fold)** — наприклад, головне Hero-зображення, логотип у шапці сайту тощо.
- **Чому:**
  * Якщо застосувати lazy loading до зображення на першому екрані, браузер призупинить його завантаження до повної побудови розмітки сторінки. Це штучно затримає появу основного візуального контенту, що суттєво погіршить показник **LCP** та загальний користувацький досвід.

### 4. Що таке файл robots.txt та яку роль він відіграє у технічному SEO? Чим відрізняються директиви `Disallow` та `Allow`?
**Robots.txt** — це простий текстовий файл, розміщений у кореневій директорії сайту, який містить інструкції для пошукових роботів (краулерів) щодо того, які сторінки чи розділи сайту їм дозволено сканувати для подальшого індексування, а які — ні.
- **Роль у SEO:** Керує "краулінговим бюджетом" (спрямовує ботів сканувати лише корисні сторінки, захищаючи сервер від зайвих запитів до службових папок, кошиків, пошукових результатів чи панелей адміністрування).
- **Різниця між директивами:**
  * `Disallow` — забороняє пошуковому боту доступ до вказаного шляху (наприклад, `Disallow: /admin/` закриє адмін-панель).
  * `Allow` — явно дозволяє сканування певного файлу чи підпапки всередині вже забороненого розділу (наприклад, дозволити сканувати один скрипт всередині закритої папки: `Allow: /wp-admin/admin-ajax.php`).

### 5. Навіщо потрібна XML Sitemap, якщо пошукові боти можуть знаходити сторінки самостійно через посилання? У яких ситуаціях Sitemap є особливо важливою?
**XML Sitemap (карта сайту)** — це спеціальний XML-файл, що містить повний структурований список усіх важливих URL-адрес сайту разом із метаданими про них (дата останньої зміни, пріоритетність, частота оновлення).
- **Навіщо потрібна:** Допомагає пошуковим системам знаходити нові або приховані сторінки значно швидше та ефективніше, ніж звичайний обхід посилань.
- **Особливо важлива в ситуаціях:**
  * **Нові сайти:** На них мало або зовсім немає зовнішніх посилань (беклінків), тому пошукові боти не зможуть виявити сайт самостійно.
  * **Великі портали або інтернет-магазини:** Сайти з великою кількістю сторінок, які часто змінюються або глибоко вкладені в структуру меню.
  * **Слабка внутрішня перелінковка:** Коли деякі корисні сторінки є ізольованими ("оріhead" сторінки) і на них немає прямих посилань з інших розділів.
  * **Наявність багатого медіаконтенту:** Дозволяє передавати метадані про відео- та фотоматеріали безпосередньо в Google Search.

### 6. Як атрибути `width` та `height` в тегах зображень впливають на показник CLS? Що відбудеться, якщо їх не вказати?
- **Вплив на CLS:** Вказуючи `width` та `height` (наприклад, `width="800" height="600"`), розробник повідомляє браузеру точні пропорції зображення (aspect ratio) **до** його завантаження. Браузер миттєво резервує порожню прямокутну область відповідного розміру на сторінці під час побудови DOM-структури контенту.
- **Що відбудеться, якщо не вказати:**
  * Браузер спочатку виділить під зображення область розміром 0x0 пікселів.
  * Коли файл зображення завантажиться через мережу, браузер раптово виявить його справжні розміри і змушений буде перебудувати весь макет сторінки (reflow).
  * Контент, що знаходився під зображенням (текст, кнопки), різко зсунеться вниз. Це створює ефект "стрибаючого макету", який дратує користувачів і призводить до високих значень показника **CLS (Cumulative Layout Shift)**, штрафуючи сайт у пошуковій видачі.

### 7. Чому зміни у польових даних (Field Data) PageSpeed Insights відображаються із затримкою після оптимізації сайту? Яке джерело даних є більш актуальним для оцінки результатів щойно виконаних змін?
- **Причина затримки польових даних (Field Data):** Польові дані збираються на основі реального досвіду користувачів (Chrome User Experience Report — CrUX) за останні **28 днів**. Тому будь-які щойно впроваджені зміни фізично не можуть миттєво оновити цю статистику — для цього потрібен час на збір нових реальних сесій відвідувачів.
- **Актуальне джерело даних для швидкої оцінки:** **Лабораторні дані (Lab Data)** або показники інструменту **Lighthouse / PageSpeed Insights Lab Report**. Вони розраховуються миттєво в реальному часі на основі симуляції завантаження сторінки безпосередньо під час запуску тестування, що дозволяє відразу побачити ефект від оптимізацій.
